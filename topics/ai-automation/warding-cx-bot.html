1. 왜 만들었나문제 → 접근 → 결과

문제

같은 수작업이 반복된다

앱 문의 폼으로 "선수 계정 추가·교체" 요청이 오면 백오피스에서 선수 조회, Riot 계정 검증, 기존 계정 확인, 부착, 이미지 확인, 안내 메일까지 사람이 순서대로 처리했다.

접근

순서가 정해진 일은 템플릿으로

문의가 올라오는 Discord 채널에 봇을 붙였다. 자연어 해석은 Codex에, 조회·판정·쓰기는 코드에 맡기고, 실제 반영은 사람이 ✅ 한 번으로 승인한다.

결과

검토만 사람이 한다

문의가 오면 봇이 스레드에 제안과 메일 미리보기를 올린다. 사람은 내용을 보고 ✅만 누르면 부착, 이미지 업로드, 안내 메일 발송이 이어진다.

2. 동작 과정문의 한 건이 들어와서 끝날 때까지

읽기·일반 호출 사람이 하는 단계 실서비스에 쓰는 단계 응답

⑥까지는 어떤 것도 바꾸지 않는다. 실서비스에 쓰기가 일어나는 건 ⑨(부착, 이미지)와 ⑪(메일)뿐이고, 그 앞에는 반드시 ⑦의 사람 승인과 ⑧의 경기 창 게이트가 있다.

이미지 처리 (뒤에 추가한 흐름)

  • 제안 단계에서 선수의 이미지가 비어 있으면 스레드에 🖼️ 이미지 없음이 표시된다.
  • 허용된 사용자가 그 스레드에 이미지를 올리면 봇이 접수 확인을 답장한다. 형식은 Content-Type이 아니라 파일 앞부분(매직바이트)으로 검사하고 png/jpg/webp, 2MB 이하만 받는다.
  • ✅를 누르면 계정 부착과 함께 이미지 업로드 API로 올라간다. 이미지가 이미 있는 선수에게는 아무 표시도 하지 않는다.

실행 구조: 무엇이 계속 돌고 무엇이 잠깐 도나

구분프로세스수명하는 일
상주node bot.js맥미니 LaunchAgent가 부팅 때 띄우고 죽으면 재기동Discord 게이트웨이 연결 유지(WebSocket), 메시지·✅ 이벤트 수신, API 호출, 메일 발송
일회성codex exec문의 1건당 자식 프로세스 1개, JSON을 뱉으면 종료원문 → JSON 변환만. 읽기 전용 샌드박스, 토큰 없음
  • Codex는 감시하지 않는다. 상주하는 건 봇뿐이고, 문의가 없으면 Codex 프로세스도 없다.
  • 이벤트 기반이라 폴링이 없다. 메시지가 오면 messageCreate, ✅가 눌리면 messageReactionAdd 핸들러가 돈다.
  • Codex 호출은 stdin으로 프롬프트를 넘기고 --output-schema로 JSON 형태를 강제해 결과 파일로 받는다. 문의 1건이 Plus 사용량 1회를 쓴다.
  • admin 액세스 토큰(30분)은 봇이 리프레시 토큰으로 필요할 때 갱신한다. 리프레시 토큰은 0600 파일에만 있다.
  • 대기 중인 제안은 봇 메모리에만 있다. 재시작하면 사라져서 문의를 다시 올려야 한다.

3. 판정과 차단 규칙Codex가 아니라 코드가 결정한다

상태조건✅ 이후 동작
created선수의 기존 솔랭 계정이 0개부착 → 응답 검증 → 메일("등록을 완료했습니다")
updated기존 계정 1개, 요청 계정과 다름교체 부착 → 응답 검증 → 메일("정상적으로 수정 완료하였습니다")
already요청 계정이 이미 같음변경 없음 → 메일("기존에 동일하게 등록되어 있는 상태입니다")
manual기존 계정 2개 이상자동 진행 안 함. 부착 API가 계정 목록을 통째로 덮어써서 다른 계정이 사라질 수 있기 때문이다.

그 밖에 자동 진행을 막는 경우

  • 이름으로 선수를 한 명으로 특정할 수 없음(동명, 미등록)
  • Riot 계정이 없거나 KR, NA, EUW 어디에도 기록이 없음
  • 항목 중 하나라도 위 사유에 걸리면 ✅ 버튼 자체를 달지 않는다(전부 또는 아무것도 아님)
  • 경기 창: 진행 중 경기가 있거나 시작 1시간 전부터는 쓰기를 거절한다. 경기 후 ✅를 다시 누르면 재시도된다.
  • 이메일이 없으면 부착만 하고 메일은 건너뛴다.
// 판정은 이 정도로 단순하다 (logic.js)
export function decide(accounts, riotId) {
  if (accounts.some((a) => normId(a.riotId) === normId(riotId))) return 'already';
  if (accounts.length === 0) return 'created';
  if (accounts.length === 1) return 'updated';
  return 'manual';
}

4. 설계 결정왜 이렇게 나눴나

역할 분리

Codex는 파싱만 한다

문의 원문을 {type, email, items[]} JSON으로 바꾸는 한 번의 호출뿐이다. 읽기 전용 샌드박스에서 돌고 DB, 네트워크, 파일 도구가 없다. 결과는 스키마(--output-schema)로 형식을 강제한다.

결정적 로직은 코드

조회·판정·쓰기는 코드

Codex가 엉뚱한 선수를 뽑아도 코드가 DB에서 다시 확인하고 이상하면 수동 처리로 넘긴다. 안전장치가 모델 밖에 있다.

사람 승인

쓰기 전에 ✅ 한 번

오부착은 되돌리는 API가 없다. 그래서 자동 승인 대신 제안, 미리보기, 승인의 3단계로 두었다. 승인자는 허용 목록의 사용자만이다.

자격증명 격리

admin 토큰은 봇만 갖는다

Codex에는 토큰이 전달되지 않는다. 봇 전용 admin 계정의 리프레시 토큰을 파일(0600)로 보관하고, 사용 때마다 로테이션한다. 문의 원문은 "데이터"로 감싸서 본문 속 지시문을 따르지 않게 했다.

기존 자산 재사용

백오피스 API와 메일 문구

새 API를 만들지 않았다. 백오피스가 쓰던 검증·부착·이미지 API를 그대로 호출한다. 메일은 실제로 발송했던 문구를 수집해 템플릿으로 만들었다.

단순함

일부러 안 한 것

대기 중인 제안은 메모리에만 두었다(재시작하면 문의를 다시 붙여넣으면 됨). 슬래시 커맨드, 신규 선수 생성은 필요가 확인될 때까지 미뤘다.

5. AI 활용 방식면접에서 설명할 포인트

1) 추측 대신 근거를 모은 뒤 설계

"이전에 어떻게 처리했는지"를 AI가 직접 찾았다. 백오피스 레포의 PR(검증 버튼, 계정 부착), 백엔드 admin API, 운영 DB의 읽기 조회, 브라우저로 열어본 실제 발송 메일에서 기존 절차와 문구를 뽑아 설계의 입력으로 삼았다.

2) 계획 → 승인 → 구현 순서

구현 전에 계획 문서를 만들고 사용자가 승인한 뒤 코드를 썼다. 선택지가 갈리는 곳(승인 방식, 토큰 방식, 이미지 범위)은 질문으로 합의했다.

3) LLM의 자리를 좁게 잡기

비결정적인 일(자연어 → 구조화)만 모델에 맡기고, 판정·쓰기·메일은 코드로 두었다. 모델이 틀려도 피해가 쓰기까지 번지지 않는 구조다.

4) 실측으로 검증

자체 테스트(판정, 경기 창, 메일 렌더링, 이미지 형식), Codex 파싱 실측, SMTP는 발송 없이 로그인만 확인(verify()), 드라이런 모드로 실서비스에 쓰기 없이 전체 흐름 확인 순서로 진행했다.

5) 위임 경계는 도구가 막아주기도 했다

운영 계정 권한 부여, 비밀값 저장, 실서비스 스위치(DRY_RUN=0)처럼 위험한 단계는 권한 분류기가 차단했다. 우회하지 않고 사람이 직접 하는 단계로 돌렸고, 그 단계의 명령과 이유는 AI가 정리해 주었다.

6) 실수를 인정하고 바로잡기

앱 비밀번호를 옮겨 적다 오타를 낸 것을 인증 실패 후 스스로 대조해 찾아 고쳤다. 비밀값이 대화에 노출된 건 마지막에 폐기·재발급 대상으로 명시해 두었다.

한 줄 요약 — AI를 "코드를 대신 쓰는 도구"가 아니라 "조사하고, 설계안을 내고, 검증까지 돌리는 동료"로 쓰되, 실서비스에 쓰는 마지막 한 걸음은 사람이 승인하도록 경계를 그었다.

7. 막힌 곳과 해결증상 → 원인 → 조치

증상원인 파악조치
봇이 메시지에 반응하지 않고 로그도 없음Discord API를 봇 토큰으로 직접 호출해 서버 참가는 정상, 채널 조회만 403 Missing Access임을 확인했다. 이벤트가 아예 안 오는 원인을 코드 문제가 아니라 채널 권한으로 좁혔다.해당 채널에 봇의 보기·전송·스레드 권한 추가
메일 SMTP 535 Username and Password not accepted일반 계정 비밀번호는 거부된다. 앱 비밀번호로 바꿨는데 또 실패해서 대조해 보니 옮겨 적다 한 글자를 빠뜨린 내 오타였다.앱 비밀번호 사용, 오타 수정 후 verify()로 발송 없이 인증만 재확인
.env가 명령어 한 줄로 덮임클립보드에 값이 아니라 직전에 복사한 명령어가 들어 있었다. 값은 노출되지 않았다.비밀값은 대화에 붙이지 않고 클립보드나 포털의 복사 버튼으로만 옮기도록 절차 재설계
봇을 비공개로 바꾸려 하니 저장 거부비공개 앱은 설치 탭의 기본 승인 링크가 "없음"이어야 한다는 포털 오류내가 추가로 건드린 설정이라 원래대로 되돌리고 필요한 Intent만 저장
"이미지 없음"이 안 뜸DB를 읽기 전용으로 확인하니 그 선수는 이미 이미지가 있고 잠금도 걸려 있었다.정상 동작. 이미지 없는 선수에게만 표시한다.
리프레시 토큰이 로테이션되지 않음서버가 같은 토큰을 돌려주는 설계(클라이언트 호환)라서, 대화에 노출된 토큰이 계속 유효하다.마무리 때 재로그인으로 새 토큰 발급, 옛 토큰은 서버 쪽에서 정리하는 항목으로 기록
